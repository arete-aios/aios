# MIT7 daily method

Main instruction: [SKILL.md](../SKILL.md). First run: [INSTALL.md](../INSTALL.md). Version 1.0.0, consolidated community method.

## 1. Define the day’s goal

Use the user’s accepted direction and current priorities. Establish date/timezone and whether the request is a proposal, continuation of an accepted plan or closeout. Preserve existing pauses and permissions. A guide/explanation request performs only method/view work.

Output: the day’s question and authorised scope. A useful example is “with 100 available minutes, finish one artifact ready for a client decision”. This is not an accepted daily selection yet.

## 2. Reconcile current evidence

Read the relevant project’s latest decision, delivered artifact and user confirmation. Compare those with card status, current attention and source-backed commitments. Show conflicting sources and dates rather than silently choosing the oldest task. A delivered artifact may need acceptance or use; it need not be recreated.

Define source authority explicitly: your chosen tracker stores the selection/status fields assigned to it; the project home stores context, decisions and evidence; current priorities express accepted attention. A card alone is not delivery evidence. Do not create a parallel database just for this method. Use only communication context you are authorised to read.

Output: a short candidate rationale with source, observation date and unknowns. Lasting facts remain in their existing project home.

## 3. Check capacity

Read the authorised calendar or use the user’s stated work windows. Include fixed commitments, preparation and transitions. Keep required user minutes separate from AI work. Estimates are not guarantees.

Without calendar access, mark the stated window “calendar not verified”. Without any window, prepare provisional candidates and identify the missing input. A calendar conflict does not itself authorise moving an event.

Output: available user minutes and the assumptions behind each estimate. If a 90-minute outcome has only 30 minutes available, reduce the achievable endpoint or defer it; do not merely shrink the number.

## 4. Propose outcomes and let the user choose

Propose at most three meaningful outcomes using strategic value, accepted commitments, unblocking effect, readiness and capacity. A busy day may have one or no additional outcome. Waiting without an available user action is not itself a finishable daily outcome.

For each candidate show why today, a testable done criterion, source, next action, responsible person, minutes and dependency. Several cards may form one outcome: topic approval and a materials package may together mean “ready to lead the lesson”. Card count and outcome count differ. Respect the selected tracker’s actual limits and expose the mapping.

The user chooses. A suggestion or assignee name is not acceptance or execution. After a clear decision, save only authorised changes in the existing tracker, then read back the date, selected records and estimates. Preserve previous selection history; do not repeat an approval already clearly given.

Output: either a proposal or a clearly accepted selection with verification. Label which one it is.

## 5. Prepare and deliver authorised work

AI prepares or delegates the specific assigned work within existing permission. A domain method performs the delivery; MIT7 coordinates the result and next action. External sending, publishing, payments, access changes or schedules follow the actual task authorisation.

Read current records before editing, use the adapter’s available concurrency checks, and read back after an ambiguous error rather than blindly repeating a write. If a tracker is unavailable, provide a clear proposed change and state that the live record was not saved.

Output: the artifact and evidence in the existing project home, with an authorised status/next-action update in the same tracker. Keep private deliveries out of this reusable skill folder.

## 6. Close and preserve

For each accepted outcome record completed with done evidence; waiting with what/from whom; blocked with a concrete obstacle or decision needed; or continuing with the remaining work. Give the next action and responsible person. A date comes from an actual commitment or is labelled as a proposal. Unfinished work does not automatically become tomorrow’s selection.

Keep a dated closeout in the existing project/day record and link the relevant cards. Current card status may change later; it is not an immutable record of a past evening. State the actual selection date rather than automatically saying “yesterday”.

Output: a dated result, evidence, waiting/blocking reason and next step with preserved history. No automatic morning or evening process is installed by this package.

## AIOS contribution and standalone use

This is a qualitative dependency description, not an accuracy score. Integration is medium for standalone planning and high when a personalised system supplies accepted direction, current evidence and real tool state.

| Layer | Input → decision → benefit |
| --- | --- |
| Constitution | Direction and permissions → choose valuable permitted outcomes → attention advances an accepted goal. |
| Memory | Latest decisions and delivery evidence → avoid recreating completed work → the next step starts from reality. |
| Skills | Relevant communication/planning context and domain methods → grounded candidates and actual delivery → selection connects to execution. |
| Tools | Calendar and one chosen tracker → feasible minutes, saved choice and readback → verifiable state. |
| Focus | Accepted current priorities → narrow candidates → a new suggestion does not silently replace the direction. |

Standalone use needs direction, current facts, commitments, a time window and one list. Without connections, AI works from supplied text and labels unknowns. It cannot claim a live calendar check, saved external selection or ongoing monitoring. No new database is required.
